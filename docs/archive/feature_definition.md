## 2. 인증 (Auth)

### 2-1. 아이디 중복 확인

| 항목 | 내용 |
|------|------|
| **기능명** | 아이디 중복 확인 |
| **설명** | 회원가입 전 원하는 아이디(username)의 사용 가능 여부를 실시간으로 확인한다. |
| **API** | `GET /auth/check-username?username={username}` |
| **사용자 흐름** | 사용자가 아이디 입력 필드에 타이핑 → 중복 확인 요청 → 사용 가능 여부 즉시 표시 |
| **비즈니스 규칙** | 이미 사용 중인 username이면 `available: false` 반환, 사용 가능하면 `available: true` 반환 |
| **MVP** | ✅ |

### 2-2. 회원가입 (Step 1)

| 항목 | 내용 |
|------|------|
| **기능명** | 회원가입 |
| **설명** | 이메일·아이디·비밀번호·약관 동의를 입력받아 계정을 생성하고 즉시 로그인 상태로 전환한다. |
| **API** | `POST /auth/register` |
| **사용자 흐름** | 회원가입 폼 작성 → 약관 동의 → 계정 생성 → Access Token + Refresh Token 응답 수신 → 앱 보안 저장소에 Refresh Token 저장 → 온보딩 Step 2로 이동 |
| **비즈니스 규칙** | ① 비밀번호 BCrypt 해싱 저장 ② 이메일·username 중복 시 400 에러 ③ 회원가입 완료 시 `onboarding_completed: false` 상태로 온보딩 흐름 진입 |
| **MVP** | ✅ |

### 2-3. 로그인

| 항목 | 내용 |
|------|------|
| **기능명** | 로그인 |
| **설명** | 이메일·비밀번호로 인증하고 Access Token과 Refresh Token을 발급한다. |
| **API** | `POST /auth/login` |
| **사용자 흐름** | 로그인 폼 입력 → 인증 성공 → `onboarding_completed` 값에 따라 온보딩 화면 또는 My Bar 메인으로 이동 |
| **비즈니스 규칙** | ① 인증 실패 시 `AUTH_001` ② `onboarding_completed: false`이면 온보딩 Step 2부터 재개 ③ Refresh Token은 DB에 저장되며 응답 body로 반환 |
| **MVP** | ✅ |

### 2-4. 토큰 재발급 (Token Rotation)

| 항목 | 내용 |
|------|------|
| **기능명** | Access Token 재발급 |
| **설명** | 만료된 Access Token을 Refresh Token으로 갱신한다. Rotation 전략을 적용해 매 재발급 시 새 Refresh Token을 발급한다. |
| **API** | `POST /auth/refresh` |
| **사용자 흐름** | 클라이언트가 API 호출 시 401 수신 → 앱 보안 저장소의 Refresh Token으로 재발급 요청 → 새 Access Token과 Refresh Token 저장 → 원래 요청 재시도 |
| **비즈니스 규칙** | ① Refresh Token 만료 또는 무효 시 `AUTH_006` → 로그인 화면 이동 ② 재발급 성공 시 기존 Refresh Token 무효화 및 새 토큰 저장 |
| **MVP** | ✅ |

### 2-5. 로그아웃

| 항목 | 내용 |
|------|------|
| **기능명** | 로그아웃 |
| **설명** | 서버의 Refresh Token을 삭제하여 세션을 종료한다. |
| **API** | `POST /auth/logout` |
| **사용자 흐름** | 로그아웃 버튼 클릭 → 서버에서 Refresh Token 삭제 → 로그인 화면으로 이동 |
| **비즈니스 규칙** | 200 성공 응답 반환, 서버 측 Refresh Token 삭제 |
| **MVP** | ✅ |

### 2-6. 비밀번호 재설정

| 항목 | 내용 |
|------|------|
| **기능명** | 비밀번호 재설정 |
| **설명** | 이메일로 재설정 링크를 발송하고, 링크 클릭 후 새 비밀번호로 변경한다. |
| **API** | `POST /auth/password/reset-request`, `POST /auth/password/reset` |
| **사용자 흐름** | 이메일 입력 → 재설정 링크 이메일 수신 → 링크 클릭 → 새 비밀번호 입력 → 변경 완료 |
| **비즈니스 규칙** | ① 이메일 미존재 여부와 상관없이 동일 응답 (보안상 이메일 열거 방지) ② 재설정 토큰 만료 또는 무효 시 `AUTH_007` |
| **MVP** | ✅ |

## 3. 사용자 (User)

### 3-1. 온보딩 Step 2 — 기본 정보 입력

| 항목 | 내용 |
|------|------|
| **기능명** | 기본 정보 설정 (온보딩) |
| **설명** | 회원가입 직후 성별·나이대·음주 빈도를 입력받아 프로필을 구성한다. |
| **API** | `PATCH /users/me/profile` |
| **사용자 흐름** | 온보딩 Step 2 화면 → 성별·나이대·음주 빈도 선택 → 저장 → Step 3으로 이동 |
| **비즈니스 규칙** | 해당 정보는 취향 기반 추천 및 커뮤니티 프로필에 활용된다. |
| **MVP** | ✅ |

### 3-2. 온보딩 Step 3 — 취향 설정

| 항목 | 내용 |
|------|------|
| **기능명** | 취향 설정 (온보딩) |
| **설명** | 맛 취향(복수 선택)·선호 도수 범위·경험 수준을 입력받아 레시피 추천의 초기 데이터로 활용한다. |
| **API** | `POST /users/me/preferences` |
| **사용자 흐름** | 온보딩 Step 3 화면 → 취향 선택 → 저장 → `onboardingCompleted: true`로 업데이트 → My Bar 메인 이동 |
| **비즈니스 규칙** | 취향 저장과 동시에 `users.onboarding_completed = true` 처리. 이후 레시피 콘텐츠 필터링에 즉시 반영 |
| **MVP** | ✅ |

## 5. 레시피 (Recipe)

### 5-1. 레시피 홈 — 재고 기반 추천
